# 운영 롤백 절차

> 상시 문서다 — 완료되어 아카이브되지 않는다. 배포 구조가 바뀌면 이 문서도 함께 고친다.
> 최초 작성: 2026-09-02 · 기준 브랜치: `chore/rollback-procedure` · 기준 HEAD: `a98a860`

장애 상황에서 처음부터 알아내지 않도록, 필요한 판단과 명령을 한곳에 모은다.

---

## 먼저 — Coolify 대시보드의 "Redeploy"는 롤백이 아니다

Coolify는 `ghcr.io/cow-mju-craft/cowmjucraft:latest`를 바라본다. 배포는 매번 `:latest`와 `:<커밋 SHA>` 두 태그를 밀고, Coolify는 `:latest`만 당겨온다.

따라서 대시보드에서 이전 배포를 골라 **Redeploy를 눌러도 같은 `:latest`를 다시 당겨오고, 나쁜 버전이 그대로 다시 뜬다.** 배포 이력에는 새 항목이 생겨 롤백된 것처럼 보이지만 실제로 바뀐 것은 없다.

**실제 롤백은 `:latest`가 가리키는 대상을 이전 SHA 이미지로 바꾸는 것이다.** `Rollback (production)` 워크플로우가 이 일을 한다.

---

## 1. 롤백할지, 앞으로 고칠지 판단한다

**롤백하지 말고 hotfix로 가야 하는 경우**

- **되돌릴 배포에 DB 마이그레이션이 포함돼 있다** — 아래 § DB 제약 참조. 대부분의 경우 이쪽이다
- 원인이 명확하고 수정이 한 줄이며, 재배포까지 걸리는 시간이 장애 지속 시간보다 짧다
- 롤백 대상 버전에도 같은 문제가 있다

**롤백이 맞는 경우**

- 원인이 불분명한데 직전 배포 이후에 문제가 시작됐다
- 마이그레이션 없는 코드 변경만 있었다
- 수정에 시간이 걸리고 그동안 서비스가 망가진 상태로 남는다

판단이 안 서면 **롤백이 기본값**이다. 먼저 서비스를 살리고 원인은 그다음에 찾는다.

---

## 2. 되돌아갈 SHA를 찾는다

되돌아갈 대상은 **마지막으로 정상 배포된 커밋**이다.

- GitHub Actions → `Build & Push to ghcr.io` 워크플로우 실행 목록에서 **smoke check까지 통과한** 최근 실행을 찾는다. 그 실행이 빌드한 커밋 SHA가 대상이다
- 또는 `git log --first-parent origin/main` 으로 직전 병합 커밋을 확인한다

SHA는 **40자 전체**를 쓴다. 이미지 태그가 전체 SHA로 붙어 있어 축약형(`abc1234`)으로는 이미지를 찾지 못한다.

```bash
git rev-parse origin/main~1
```

---

## 3. 롤백 워크플로우를 실행한다

GitHub → Actions → **Rollback (production)** → Run workflow

| 입력 | 값 |
|---|---|
| `sha` | 2번에서 찾은 40자 커밋 SHA |
| `reason` | 롤백 사유 (기록으로 남는다) |

워크플로우가 하는 일:

1. SHA 형식 검증 (40자 16진수)
2. GHCR에 해당 이미지가 실제로 있는지 확인 — 없으면 즉시 중단
3. 롤백 직전 `:latest` 다이제스트를 실행 요약에 기록 (되돌리기 필요 시 근거)
4. **레지스트리 안에서 `:latest`를 대상 SHA로 재태깅** — 이미지를 내려받지 않아 몇 초면 끝난다
5. Coolify 웹훅 호출
6. deploy와 동일한 smoke check — 실제 JSON 응답을 20회까지 재시도하며 확인

`deploy.yml`과 같은 concurrency 그룹(`deploy-main`)을 쓴다. **롤백 중에는 main에 push하지 않는다** — 새 배포가 큐에 들어가면 방금 되돌린 것이 다시 덮인다.

---

## 4. DB 제약 — 코드는 되돌아가지만 스키마는 안 된다

**롤백에서 가장 중요한 부분이다.**

스키마 변경은 Flyway 마이그레이션으로만 이뤄지고, Flyway에는 되돌리기(down migration)가 없다. `V5`가 적용된 DB에 `V5`를 모르는 이전 jar를 띄우면, Flyway는 "DB에 적용된 마이그레이션이 로컬에 없다"고 판단해 **부팅을 거부하는 것이 기본 동작**이다. 즉 롤백을 시도했다가 앱이 아예 뜨지 않을 수 있다.

> ⚠️ 확인 필요: 이 레포의 `application-prod.yml`에 `spring.flyway.validate-on-migrate`나 `ignore-migration-patterns`가 어떻게 설정돼 있는지에 따라 동작이 달라진다. 위 서술은 Flyway/Spring Boot 기본값 기준이다. 실제 설정을 확인해 이 문단을 확정할 것.

**그래서 지켜야 할 규칙 — 마이그레이션은 항상 하위 호환으로 쓴다.**

| 안전 (이전 버전 코드가 계속 동작) | 위험 (이전 버전 코드를 깨뜨림) |
|---|---|
| 컬럼 추가 (nullable 또는 기본값 있음) | 컬럼 삭제 |
| 테이블 추가 | 컬럼 이름 변경 |
| 인덱스 추가 | 기존 컬럼에 NOT NULL 추가 |
| | 타입 축소 (VARCHAR 길이 줄이기 등) |

삭제·이름 변경이 필요하면 **두 번의 배포로 나눈다.** 먼저 코드에서 사용을 중단해 배포하고, 그것이 안정된 뒤 다음 배포에서 컬럼을 제거한다. 이렇게 하면 각 배포는 언제든 롤백 가능한 상태로 유지된다.

---

## 5. 롤백이 실패하면

smoke check가 실패했다면 되돌린 버전도 뜨지 못한 것이다. 대개 4번의 DB 문제다.

1. Coolify에서 컨테이너 로그를 본다 — Flyway 검증 실패인지 다른 원인인지 구분한다
2. Flyway 문제라면 **더 뒤로 가는 롤백은 상황을 악화시킨다.** 앞으로 고치는 방향(hotfix)으로 전환한다
3. 롤백 워크플로우 실행 요약에 기록된 **롤백 직전 `:latest` 다이제스트**로 원상복구할 수 있다
